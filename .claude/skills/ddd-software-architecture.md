# 软件架构开发技能

本技能为高质量软件开发和架构提供指导，基于整洁架构（Clean Architecture）和领域驱动设计（DDD）原则。

## 代码风格规则

### 通用原则

- **早返回模式（Early Return）**：在可能的情况下，始终使用早返回而非嵌套条件，以提高可读性
- 通过创建可复用的函数和模块来避免代码重复
- 分解过长（超过 80 行代码）的组件和函数为多个较小的组件和函数。如果无法在别处使用，就保持在同一文件中。但如果文件超过 200 行代码，应该拆分为多个文件。
- 尽可能使用箭头函数而非函数声明

### 最佳实践

#### 库优先原则

- **在编写自定义代码之前，始终搜索现有解决方案**
  - 检查 npm 是否存在解决问题的现有库
  - 评估现有的服务/SaaS 解决方案
  - 考虑使用第三方 API 实现常见功能
- 使用库而非编写自己的工具函数。例如，使用 `cockatiel` 而非自己编写重试逻辑。
- **当自定义代码是合理的时候：**
  - 特定于领域的独有业务逻辑
  - 具有特殊要求的性能关键路径
  - 当外部依赖过度时
  - 需要完全控制的安全敏感代码
  - 在彻底评估后现有解决方案不满足需求时

#### 架构与设计

- **整洁架构和 DDD 原则：**
  - 遵循领域驱动设计和通用语言
  - 将领域实体与基础设施关注点分离
  - 保持业务逻辑独立于框架
  - 清晰定义用例并保持隔离
- **命名约定：**
  - **避免** 通用名称：`utils`、`helpers`、`common`、`shared`
  - **使用** 领域特定名称：`OrderCalculator`、`UserAuthenticator`、`InvoiceGenerator`
  - 遵循有界上下文命名模式
  - 每个模块应有单一、清晰的目的
- **关注点分离：**
  - 不要将业务逻辑与 UI 组件混合
  - 将数据库查询保持在控制器之外
  - 保持上下文之间的清晰边界
  - 确保职责正确分离

#### 需要避免的反模式

- **NIH（不是这里发明）综合症：**
  - 当 Auth0/Supabase 存在时不要构建自定义认证
  - 不要编写自定义状态管理而应使用 Redux/Zustand
  - 不要创建自定义表单验证而应使用成熟的库
- **糟糕的架构选择：**
  - 将业务逻辑与 UI 组件混合
  - 数据库查询直接在控制器中
  - 缺乏清晰的关注点分离
- **通用命名反模式：**
  - `utils.js` 包含 50 个不相关的函数
  - `helpers/misc.js` 作为垃圾堆
  - `common/shared.js` 目的不明确
- 记住：每一行自定义代码都是需要维护、测试和文档化的负担

#### 代码质量

- 使用类型化 catch 块进行适当的错误处理
- 将复杂逻辑分解为更小、可复用的函数
- 避免深层嵌套（最多 3 层）
- 保持函数专注，可能的话控制在 50 行以内
- 保持文件专注，可能的话控制在 200 行以内
