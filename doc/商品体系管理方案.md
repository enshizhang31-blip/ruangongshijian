# 商品体系管理方案

> 本文档定义 SPU / SKU / SN码 三层商品体系的管理规则、操作流程和注意事项。
> 关联文档：[需求详细设计.md](doc/2026-03-27-需求详细设计.md)、[数据库设计.md](doc/2026-03-28-数据库设计.md)、[国际化方案.md](doc/2026-03-29-国际化方案.md)

## 一、三层体系速览

```
                 ┌──────────────┐
                 │   分类       │  如：手机 / 电脑 / 配件
                 │  Category    │
                 └──────┬───────┘
                        │ 1:N
                 ┌──────▼───────┐
                 │    SPU       │  如：iPhone 15 Pro  ←  抽象概念，无价格
                 │   (Goods)    │
                 └──────┬───────┘
                        │ 1:N
                 ┌──────▼───────┐
                 │    SKU       │  如：iPhone 15 Pro 黑色 256G  ←  价格在此
                 │   (Sku)      │
                 └──────┬───────┘
                        │ 1:N
                 ┌──────▼───────┐
                 │   SN码       │  如：SN202503010001  ←  实物在此
                 │  (SnCode)    │
                 └──────────────┘
```

| 层级 | 数据表 | 是什么 | 有没有价格 | 有没有库存 |
|------|--------|--------|:---:|:---:|
| **SPU** | `goods` | 商品抽象概念 | ❌ | ❌ |
| **SKU** | `sku` | 规格组合（SPU + 颜色 + 容量 + ...） | ✅ `price` | ❌（动态算） |
| **SN码** | `sn_code` | 具体实物，每台一个唯一编号 | ✅(冗余) | ✅ 按 status=0 计数 |

## 二、SPU 管理

### 2.1 SPU 是什么

SPU = Standard Product Unit，是商品信息的容器。它只存储与规格无关的信息：

| 字段 | 说明 | 示例 |
|------|------|------|
| `name` | 商品名称 | `iPhone 15 Pro` |
| `categoryId` | 所属分类 | `1`（手机） |
| `brand` | 品牌 | `Apple` |
| `imageUrl` | 主图 | `https://...` |
| `images` | 多图 JSON | `["url1","url2"]` |
| `shortDesc` | 短描述(卡片展示) | `苹果最新旗舰手机` |
| `description` | 详细描述 | `采用A17 Pro芯片...` |
| `status` | 上下架 | `0` 下架 / `1` 上架 |

### 2.2 创建 SPU 流程

```
1. 点击【新增商品】
2. 填写基本信息：名称、品牌
3. 选择分类（手机/电脑/配件/...）
4. 上传主图和详情图
5. 填写短描述（卡片展示）和详细描述
6. 保存 → 状态为"下架(0)"
7. 继续创建 SKU →
```

### 2.3 什么时候 SPU 可以上架

```
SPU 上架条件：status=1 且有至少 1 个启用且库存 > 0 的 SKU
```

> 没有 SKU 的 SPU 不允许上架（用户看不到）。

### 2.4 SPU 与分类的关系

- 一个 SPU 只能属于一个分类
- 分类下有商品时**不允许删除**分类
- 支持多级分类（父级 -> 子级），SPU 只挂到叶子分类

## 三、规格体系（Spec）

### 3.1 规格是什么

规格 = 商品的可选属性分类。有两张表：

| 表 | 说明 | 示例 |
|----|------|------|
| `spec_name` | 规格名称 | 颜色、容量、版本、尺寸 |
| `spec_value` | 规格值 | 黑色、256G、Pro版、XL |

### 3.2 规格命名规则

```
spec_name: 全局通用，不绑定分类
spec_value: 挂靠在 spec_name 下，同一个 spec_name 可被多个 SPU 复用
```

### 3.3 创建规格

```
1. 进入"规格管理"页面
2. 新建规格名称，如"颜色"
3. 为"颜色"添加规格值：黑色、白色、蓝色、金色
4. 规格值可随时新增/删除/排序
```

### 3.4 规格值删除安全规则

```
删除规格值 → 检查是否有 SKU 引用该值
→ 有引用：禁止删除，提示"规格值已被 3 个 SKU 使用"
→ 无引用：允许删除
```

## 四、SKU 管理（核心）

### 4.1 SKU 是什么

SKU = Stock Keeping Unit，是 SPU 的规格化实例。每个 SKU 有独立的价格和库存。

| 字段 | 说明 | 示例 |
|------|------|------|
| `spuId` | 所属 SPU | `1` |
| `skuCode` | SKU 编码 | `IP15-BLK-256` |
| `specJson` | 规格组合 JSON | `{"颜色":"黑色","容量":"256G"}` |
| `price` | 销售价格 | `6999.00` |
| `costPrice` | 成本价 | `6500.00` |
| `imageUrl` | SKU 图片(可覆盖 SPU 图) | `https://...` |
| `status` | 启用/禁用 | `0` 禁用 / `1` 启用 |

### 4.2 SKU 编码规则（skuCode）

```
格式: {前缀}-{规格值缩写}-{规格值缩写}-...
示例:
  IP15-BLK-256      → iPhone 15, Black, 256G
  MB14-SLVR-512     → MacBook 14, Silver, 512G
```

**必须唯一**：同一 SPU 下 skuCode 唯一，建议全局唯一。

### 4.3 创建 SKU 流程

```
方式一：单个创建
  1. 在 SPU 详情页点击【新增SKU】
  2. 选择规格组合（颜色: 黑色 + 容量: 256G）
  3. 输入 skuCode、price、costPrice
  4. 可选：上传 SKU 专属图片
  5. 保存

方式二：批量生成（推荐）
  1. 在 SPU 详情页点击【批量生成SKU】
  2. 勾选需要的规格（颜色选 3 个 + 容量选 3 个）
  3. 系统自动计算 3×3=9 个 SKU
  4. 批量设置价格、编码前缀
  5. 一键生成
```

### 4.4 批量生成算法

```
输入: SPU + 规格1(v1,v2,v3) + 规格2(v4,v5)
输出: 3×2 = 6 个 SKU

v1-v4, v1-v5, v2-v4, v2-v5, v3-v4, v3-v5

伪代码：
function generateSkus(spu, specs[]) {
    combinations = cartesianProduct(specs.map(s => s.values))
    for combo in combinations:
        sku = new Sku()
        sku.spuId = spu.id
        sku.specJson = buildSpecJson(specs, combo)
        sku.skuCode = buildCode(spu, combo)
        sku.price = defaultPrice  // 创建后需手动修改
        save(sku)
}
```

### 4.5 SKU 库存计算（重要！）

```
库存 = SELECT COUNT(*) FROM sn_code
       WHERE sku_id = ? AND status = 0

status=0: 在库
status=1: 已售
status=2: 已作废
其他状态不计入库存
```

- **SKU 表不存库存值**，每次查询动态计算
- 前端 `Sku.stock` 是动态填充的只读字段

### 4.6 SKU 定价策略

| 场景 | 建议 |
|------|------|
| 同 SPU 下各 SKU 价格不同 | 不同容量/版本价格递增 |
| 导入时无价格 | 设为 0，需补充后才能上架 |
| 成本价 | 用于计算毛利，不影响前端展示 |

## 五、SN码管理

### 5.1 SN码是什么

SN码 = 具体实物的唯一编号。每个 SN 码对应一个 SKU。

| 字段 | 说明 |
|------|------|
| `snCode` | 唯一编号，如 `SN202503010001` |
| `skuId` | 关联的 SKU |
| `status` | 0 在库 / 1 已售 / 2 已作废 / 3 退货中 / 4 已退货 |

### 5.2 SN码状态流转

```
    ┌──────────────────────────────────────────┐
    │                                          │
    ▼                                          │
  ┌───┐   卖出   ┌───┐   退货申请   ┌───┐      │
  │ 0  │ ──────> │ 1  │ ──────────> │ 3  │      │
  │在库│         │已售│             │退货中│     │
  └───┘         └───┘             └───┘      │
    │                                │         │
    │ 作废                           │ 退货完成 │
    ▼                                ▼         │
  ┌───┐                           ┌───┐       │
  │ 2  │                           │ 4  │──────┘
  │作废│                           │已退│ 退回在库
  └───┘                           └───┘
```

### 5.3 SN码来源

| 来源 | source值 | 说明 |
|------|----------|------|
| 手动录入 | 1 | 单个输入 |
| CSV导入 | 2 | 批量上传 |
| 自动生成 | 3 | 系统自动生成 |

### 5.4 SN码生成规则

```
格式: {前缀}{日期}{序号}
示例:
  SN202503010001  → 2025年3月1日 第1个
  IP15-001        → iPhone15 第1个（按SPU前缀）
```

### 5.5 SN码操作日志

每次 SN 码状态变更，记录到 `sn_code_log` 表：

```
sn_code_log 字段:
  sn_code_id  # SN码ID
  operation   # 操作类型: 录入/销售/作废/退货
  from_status # 操作前状态
  to_status   # 操作后状态
  operator_id # 操作人
  remark      # 备注
```

## 七：常见操作场景

### 场景1：上架一个全新商品

```
1. 新建分类（如果不存在）→ "手机"
2. 新建规格值（如果不存在）→ 颜色:黑/白/金, 容量:128G/256G/512G
3. 新建SPU → iPhone 15 Pro, 分类=手机, 品牌=Apple
4. 批量生成SKU → 3颜色 × 3容量 = 9个SKU
5. 逐个设置SKU价格和成本价
6. 为每个SKU录入SN码（CSV导入或自动生成）
7. 上架SPU → 用户可见
```

### 场景2：新增一个颜色规格

```
1. spec_value 表新增 "金色" → 关联 spec_name "颜色"
2. 为所有使用"颜色"规格的SPU批量生成新颜色SKU（可选择范围）
3. 新SKU补录SN码
```

### 场景3：SN码退货处理

```
1. 订单退款/退货发起
2. 该订单涉及的SN码: status 1→3(退货中)
3. 货物入库确认后: status 3→4(已退货)
   → 此SN码重新计入库存
```

### 场景4：商品调价

```
1. 进入SPU详情 → SKU列表
2. 批量编辑价格（可逐SKU设置或统一设置）
3. 保存 → 立即生效
4. 已生成但未支付的订单不受影响
```

### 场景5：SPU 下架

```
1. SPU列表 → 点击【下架】
2. 用户端不再展示该SPU及其SKU
3. 已有订单不受影响
4. 下架后可重新上架
```

## 八：注意事项与禁止模式

### ✅ 推荐做法

| 做法 | 原因 |
|------|------|
| 先用"批量生成"创建SKU框架，再逐SKU调价格 | 避免遗漏规格组合 |
| SKU编码使用有意义的前缀 `IP15-BLK-256` | 运营一看就懂 |
| 规格名用中文，"颜色"而不是"color" | 与 specJson 存储一致 |
| SN码用CSV批量导入 | 一次成千上万条 |
| 删除前检查关联关系 | 避免级联删除导致数据丢失 |

### ❌ 禁止模式

| 禁止 | 原因 |
|------|------|
| 直接改 `specJson` 内容 | 会导致翻译和查询异常 |
| 从数据库直接删除 SPU/SKU/SN | 必须通过 API 走级联逻辑 |
| SN码库存存的负数 | 卖超没有意义，库存=0 就该下架 SKU |
| 同一个 SN码反复销售 | 一码一机，卖出后不可再售 |
| SPU 上架但没有一个 SKU 有库存 | 用户看到但买不了 |

## 九：数据约束与依赖

```
删除分类
  → 检查: 分类下是否有 SPU？
  → 有: 禁止删除
  → 无: 允许删除

删除规格值
  → 检查: 是否有 SKU 的 specJson 引用该值？
  → 有: 禁止删除
  → 无: 允许删除

删除 SPU
  → 级联: 删除所有 SKU
    → 级联: 删除所有 SN码
      → 级联: 删除所有 SN码操作日志

删除 SKU
  → 检查: SKU 下是否有在库 SN码？
  → 有: 警告确认
  → 级联: 删除所有 SN码 + 操作日志
```

## 十：SKU 生成算法详解（供开发参考）

### 笛卡尔积算法

```java
public List<Sku> generateSkus(Long spuId, List<Long> specIds) {
    // 1. 获取每个 spec 的所有 values
    List<List<SpecValue>> specValues = specIds.stream()
        .map(id -> specValueMapper.selectBySpecId(id))
        .collect(toList());

    // 2. 计算笛卡尔积
    List<List<SpecValue>> combinations = cartesianProduct(specValues);

    // 3. 为每个组合创建 SKU
    List<Sku> skus = new ArrayList<>();
    for (List<SpecValue> combo : combinations) {
        Sku sku = new Sku();
        sku.setSpuId(spuId);
        sku.setSkuCode(buildSkuCode(spuId, combo));
        sku.setSpecJson(buildSpecJson(combo));
        sku.setPrice(BigDecimal.ZERO);   // 待运营定价
        sku.setCostPrice(BigDecimal.ZERO);
        sku.setStatus(1);
        skus.add(sku);
    }
    return skus;
}

private List<List<SpecValue>> cartesianProduct(List<List<SpecValue>> lists) {
    List<List<SpecValue>> result = new ArrayList<>();
    result.add(new ArrayList<>());
    for (List<SpecValue> list : lists) {
        List<List<SpecValue>> temp = new ArrayList<>();
        for (List<SpecValue> r : result) {
            for (SpecValue v : list) {
                List<SpecValue> nr = new ArrayList<>(r);
                nr.add(v);
                temp.add(nr);
            }
        }
        result = temp;
    }
    return result;
}
```
